I want to create a framework specification for a cloud native file format for storing very large Nd vector objects, including, points clouds, skeletons, line segments, streamlines, etc. that utlizes ZARR as a backend.  These vector objects might have arbitrary levels of metadata attached to them at the level of the points, objects (line segments, skeletons, meshes), and might have groups of such objects, and metadata on those groups. 

I'd like to take build off the framework from the TRX format (https://github.com/tee-ar-ex/trx-spec/blob/master/specifications.md ) but then extend it to be utilizing ZARR as the primary backend for storing the n-dimensional arrays. 

I also want spatial indexing and multi-resolution representations to be a native part of the format, as it needs to handle reading and writing millions or trillions of points, requiring distributed uncoordinated reading and writing.  

My vision is to store underlying vertices in a N dimensional Zarr array, with ragged values. 2d point clouds could be XY, 3d points clouds could be XYZ, tracks through time could be XYZT.  These dimensions I will refer to as the spatial index (though in the case of time it's more than space). 
The values are a ragged set of bytes that contain a variable number of points/vertices.  

For the vertex positions themselves, those points will have the same number of dimensions as the spatial index. This will allow reading of all the vertex positions in a spatial index to be fast.  The metadata can allow these positions to be encoded as compressed draco, and for meshes they might also be draco, encoding the connections between those offsets directly. The implicit agreement is that the spatial locations encoded within a spatial chunk all lie within that spatial chunk, but unlike dense data, we have not required that there be a value for every finite position in the spatial dimension, and the values can in fact be floats or ints within that dimension.  Also, related to stitching objects across spatial index chunks, we can place values precisely on the borders so that de-duplication along the border can link them. 

Like TRX, vertex attributes can then be stored in seperate ZARR array with a spatial index + a channel dimension, this can allow efficient retrieval of a subset of vertex attributes on demand, for example, if you have 20K gene values on each location of your point cloud, you may want to access only one gene value, or a small range of genes. By adjusting the chunking strategy across this channel dimension, you can optimize the access pattern to your liking. 

Like TRX, a seperate Zarr array can store the groupings of points within a spatial chunk object.  This is the equivalent of the path_offsets, but is more general, in the sense that it might also reference groups of vertices that are part of the same mesh, or groups of vertices that are part of any n-d polygon. We will write the vertices that are part of the same object consecutively in the vertex positions, and/or attribute arrays, so that reading all the vertices, or vertex objects associated with a group of vertices within a spatial chunk can be done in one range read. These offsets could be encoded as "position" indices into the array, or in the case of draco encoding, could represent the bytes offsets of those objects.  This will enable the selective reading of groups of vertices from the file with one range read. 

Unlike TRX, I want to add a seperate Zarr array that can also store the links between these vertices. For skeletons, this can be done as a "parent" zarr array, where the value represents the index of the parent vertex to that vertex.  Because most "parent" values will be pointing to the previous index, this will compress after taking a diff to a very small array, but for branches, it will allow links to form across the groups, which will be individual "paths" on the branching skeleton.  For meshes that are not draco encoded, this could be a seperate set of faces.  The metadata can express each of these options as a valid form of linking vertices together into geometries, tetrahedral volumetric meshes, or quad meshes are all possibilities.

There will be a seperate index to support identifying a set of grouped points, which belong to the same object that spans the entire spatial index.  Each object has an ID, and the array contains a set of indices to reference those groups, including the spatial index + the index into the groupings array.  So in the case of a 2d set of polylines, this would be a N x 3 x ragged-dim array, where the length 3 dimension would have X,Y and then the polyline index within that XY chunk.   

The specification should provide alternatives to how the geometries can be linked across spatial index chunks.  One specification could be deduplication, where vertices should explicitly align on the borders between spatial index chunks. Another specification could allow for a seperate zarr array which creates links (edges, faces, etc) between chunks.  This would be a array with M x [2,3,etc] where for edges the first value would be the spatial index + vertex offset of one side of the edge, and the second value would be the spatial index + vertex offset of the other side of the edge.  

Like OME-Zarr, this whole structure could exist across multiple levels of downsampling allowing for large scale point clouds, skeletons, or meshes to be downsampled and placed into larger spatial chunks across the levels to facilitate multi-resolution visualization.  

In the event that spatial indexing is not relevant, the format can simply collapse the spatial index to a single dimension and the format should closely align with the existing TRX specification.
